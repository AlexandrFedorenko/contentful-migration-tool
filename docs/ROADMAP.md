## 1. Единый архив бэкапа: скачать на ПК → восстановить с ПК

**Зачем.** Самый простой способ перенести контент между аккаунтами разных клиентов (например, у двух клиентов одинаковая модель): бэкап скачивается из аккаунта A одним файлом и загружается в аккаунт B. Не нужны общие списки бэкапов и два токена одновременно.

### Как сейчас (проблемы)

- Бэкап без ассетов скачивается как `.json`, с ассетами как `.zip`.
- Восстановление с ассетами (вкладка «Local JSON + ZIP») требует загрузить **два файла по отдельности**, хотя JSON уже лежит внутри ZIP.
- Облачные бэкапы на вкладке восстановления показываются только для текущего пространства, поэтому после переключения на другой аккаунт их не видно.

### Что сделать

1. **Одна кнопка «Скачать бэкап»**, на выходе всегда один `.zip`:
   ```
   backup-<space>-<env>-<дата>.zip
   ├── manifest.json   источник (space/env), дата, счётчики, версия формата, sha256 файлов
   ├── content.json    типы контента, записи, локали, настройки редактора
   └── assets/         файлы ассетов (если бэкап с ассетами)
   ```
2. **Одно поле «Восстановить из файла»** с drag & drop:
   - принимает этот `.zip` и обычный `.json` из Contentful CLI (для совместимости);
   - сразу показывает сводку из `manifest.json`: пространство, окружение, дата, число записей и ассетов;
   - дальше работает текущий сценарий: проверка локалей и маппинг, фильтр по типам контента и локалям, страховочный бэкап цели, восстановление в фоновой задаче.
3. **Проверка целостности до импорта:** контрольные суммы, версия формата, защита от zip-bomb и path traversal (уже есть в `extractAssets`). Повреждённый или чужой файл отклоняется сразу.
4. Вкладки «Local JSON» и «Local JSON + ZIP» объединить в одну. Облачные бэкапы остаются для страховочных бэкапов и отката.

### Затрагиваемые места

- `src/server/jobs/handlers/backup.ts`: собирать единый архив с `manifest.json`.
- `src/pages/api/download-backup.ts`: одна точка скачивания архива, для старых JSON-бэкапов собирать архив на лету.
- `src/pages/api/restore.ts`, `src/server/jobs/handlers/restore.ts`: принимать один файл, распознавать `.zip` или `.json`, проверять манифест.
- `src/pages/restore.tsx`, `src/hooks/useRestore.ts`: одно поле загрузки и сводка из манифеста.
- Тесты: формат манифеста, отклонение повреждённых и чужих архивов, восстановление из `.json` и из `.zip`.

### Что учесть

- Большие бэкапы с ассетами: загрузка займёт время, размер ограничен `maxAssetSizeMB` (админка) и `request_body max_size` в `deploy/Caddyfile`.
- Файл у клиента содержит весь его контент: в интерфейсе нужна короткая подсказка о безопасном хранении.

**Оценка:** 0,5–1 день вместе с тестами.

## 2. Бэклог (идеи на обсуждение)

### Перенос между аккаунтами
- **Прямой перенос A → B одной операцией:** в форме выбираются два подключения (токен клиента A и токен клиента B). Полезно для больших пространств, где архив неудобен.
- **Предпросмотр совместимости моделей** перед переносом: каких типов контента и локалей нет в цели, какие поля отличаются.
- **Библиотека облачных бэкапов по всем пространствам** с пометкой «клиент / space / env».

### Удобство и безопасность
- **История операций с откатом в один клик**: страховочный бэкап перед операцией уже создаётся, нужен экран и кнопка «Откатить».
- **Автобэкапы по расписанию** (например, ежедневно, хранение 14 дней) с уведомлением при ошибке.
- **Безопасный релиз через environment aliases**: клон `master`, миграция, проверка, переключение алиаса, мгновенный откат.
- **Отчёт для клиента (HTML или PDF)** о выполненных работах.
- **Уведомления** (Email или Slack) о завершении долгих операций.

### ИИ (Claude API)
- **Миграции на естественном языке**: текст превращается в шаги Visual Builder, шаги проходят серверную проверку (allow-list), человек подтверждает запуск.
- **Объяснение плана миграции и оценка риска** перед запуском.
- **Разбор ошибок импорта** человеческим языком с советами по исправлению.
- **Аудит модели контента**: неиспользуемые типы, поля без валидаций, дубли.
- **Автосопоставление полей** при переносе между похожими, но не одинаковыми моделями.
- Приватность: по умолчанию отправлять только схему и метаданные, для функций, которым нужен контент, спрашивать явное согласие.
